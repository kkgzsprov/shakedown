# 3. 어댑터와 와이어 프로토콜

어댑터(adapter)는 Shakedown의 게임 쪽 절반이다. 자기 시계를 멈추고, 지금 무엇이 합법인지 계산하고, 플레이어의 입력 경로로 입력을 주입할 수 있는 것은 게임뿐이다. 그래서 어댑터는 게임 안에 있어야 한다. Shakedown은 프로토콜, 적합성 검사기, 참조 어댑터(8장)를 제공한다. 에이전트 스킬(5장)은 코딩 에이전트가 새 게임용 어댑터를 작성하도록 돕는다.

## 3.1 책임

| 부분 | 해야 할 일 |
|---|---|
| 헤드리스 실행 모드 | 시드(seed)에서 세션 하나를 고정 시뮬레이션 스텝으로 돌린다. 실제 시간 기반 타이밍과 실제 입력은 쓰지 않는다 |
| 관측 | 플레이어가 알 수 있는 것만 직렬화하고, 그 이상은 넣지 않는다 |
| 후보(candidate) | 지금 합법인 행동을 나열하고, 각각에 짧은 사실적 설명을 붙인다 |
| 결정 시점(decision point) | 언제 물을지 정하고, 시계를 멈추고, 요청을 보내고, 답을 기다린다 |
| 실행기(executor) | 선택된 행동이 끝나거나, 실패하거나, 교체될 때까지 그 행동을 매 스텝 입력 이벤트로 바꾼다 |
| 반사(reflex) | 결정을 기다릴 수 없는 위험에 한 스텝 안에 반응한다 |
| 오라클(oracle) | 매 스텝 불변 조건을 검사하고, 위반이 생기면 실행(run)을 멈춘다 |
| 텔레메트리 | 이벤트를 JSON Lines로 쓴다 |
| 입력 기록(input recording) | 주입한 입력 이벤트를 모두 기록해, 디사이더(decider) 없이 실행을 재생할 수 있게 한다 |

## 3.2 실행 모드

어댑터는 명령줄로 디사이더 모드를 받는다(플래그 이름은 게임이 정한다. 2.4절 참고).

| 모드 | 결정 주체 | 용도 |
|---|---|---|
| `rule` | 게임 안의 규칙 | 기준선, CI 스모크 테스트, 브리지 없는 실행 |
| `bridge` | stdio로 연결한 Shakedown 브리지 | 임의의 Python 디사이더로 하는 실험 |
| `tape:<file>` | 기록된 답을 순서대로 | 재현. 해시가 테이프(tape)와 다른 요청은 불일치(divergence)다 |

`rule` 디사이더는 선택 사항이지만 만드는 비용이 낮다. 이것이 있으면 어느 게임이든 네트워크 없는 기준선을 갖는다. 이와 별개로, 어댑터는 디사이더 없이 `inputs.json`을 재생할 수 있어야 한다.

실행마다 게임이 시작할 때 읽는 저장 파일이나 프로필 파일의 새 사본을 받는다. 시작 파일은 게임 저장소에 커밋된 픽스처이며, `run.json`에 그 이름이 기록된다.

## 3.3 관측

봇에게는 플레이어가 알 수 있는 것만 준다. 적 쪽 월드 모델은 보통 실제 위치를 담고 있다. 그것을 직렬화하면 플레이어가 가진 적 없는 정보가 샌다.

| 그룹 | 예 |
|---|---|
| 자신 | 위치, 부위별 체력, 상태 효과, 자세, 스태미나 |
| 장비 | 무기, 장전된 탄, 예비 탄창, 소모품 |
| 보이는 것 | 지금 플레이어 화면에 보이는 적이나 물체: 상대 방위각, 거리, 노출 정도, 처음 본 뒤 지난 초 |
| 기억 | 최근에 본 것의 마지막 위치와 경과 시간 |
| 단서 | 소리, 피격 방향 표시, HUD 경고 |
| 목표 | 현재 목표, 경로 거리, 세션의 남은 시간, 계획된 탐색 단계의 남은 시간 |
| 최근 | 마지막 몇 개 전술과 각각의 종료 방식(`done`, `failed`, `replaced`, `dropped`), 그리고 걸린 초와 이동한 미터 |

거리, 경로 길이, 시야선, 엄폐 점수 같은 수치는 모두 어댑터에서 계산한다. 디사이더에게 산수를 시키지 않는다.

여기에는 프로토타입에서 얻은 교훈 두 가지가 해당한다. `objective.time_left`가 없을 때 디사이더는 탐색과 탈출을 구분하지 못했다(1.5절). `recent`가 없을 때는 실패한 같은 전술을 0.5초마다 계속 골랐고, 밤샘 실행에서 나온 버그 두 개가 모두 이 루프였다. 요청 해시가 결정론적으로 유지되도록, 관측에는 정수나 반올림한 값을 쓴다.

무엇을 "보인다"고 칠지는 신중히 정해야 한다. 프로토타입에서 게임 자체의 가시성 플래그는 첫 시야선 검사가 돌기 전까지 참이었고, 그 검사도 화면 밖에 있는 몸체를 통과시켰다. 그래서 어댑터는 적의 가슴이 출력 프레임 안에 투영될 때만 그 적을 본 것으로 셌다. 어댑터마다 벽 뒤의 개체가 `seen`에 나타나지 않는다는 단위 테스트를 추가해야 한다.

## 3.4 후보

결정 시점마다 어댑터는 합법적 후보를 최대 12개 나열한다. 후보 하나는 실행기가 몇 초 동안 이어서 수행할 수 있는 행동이다.

| 종류 | 이름 예 | 설명에 담는 것 |
|---|---|---|
| 교전 | `engage_e2` | 대상, 거리, 노출 정도, 탄창에 남은 탄 |
| 엄폐로 이동 | `cover_c1` | 거리, 가는 동안 노출되는 초, 막아 주는 위협 |
| 후퇴 | `withdraw` | 방향과 경로 길이 |
| 수색 | `search_r4` | 방, 방문 여부, 단서가 그쪽을 가리키는지 |
| 치료 | `treat_bleed_legs` | 상처, 사용 아이템, 움직이거나 쏠 수 없는 초 |
| 재장전 | `reload` | 남은 탄, 사용 가능한 탄창 |
| 루팅 | `loot_c7` | 컨테이너, 거리 |
| 탈출 | `extract_north` | 경로 길이, 남은 시간 |
| 유지 | `hold` | 현재 행동 유지 |

이름 규칙:

- 이름에는 행동 종류와 대상 ID만 넣는다. `good_cover`처럼 판단이 담긴 이름은 피한다. 타입이 있는 결정 모델에 관한 논문([arXiv 2609.26758](https://arxiv.org/abs/2609.26758))은 선택지 이름과 정의의 대응을 바꾸자 결정이 크게 바뀌었다고 보고한다. 이때 타입 오류는 0 %로 유지됐다.
- 이름과 설명은 같은 대상을 가리켜야 한다.
- 어댑터는 결정마다 시드로 후보 순서를 섞고, 순서 시드를 요청에 쓴다. 실험 E3(9.2절)은 순서와 이름이 선택을 얼마나 바꾸는지 측정한다.

## 3.5 결정 시점

어댑터는 무슨 일이 생길 때만 묻는다.

- **이벤트.** 새 위협 발견, 위협 놓침, 피격, 대상 쓰러짐, 상처 발생, 탄약 4분의 1 미만, 현재 전술 종료 또는 실패, 시간 경고.
- **타이머.** 교전 중에는 게임 시간 0.5초마다(2 Hz 상한), 그 밖에는 3초마다.
- **유예.** 선택 후 0.5초 동안은 피격을 제외하고 새로 묻지 않는다. 그래야 전술이 매 스텝 뒤집히지 않는다.

비교 기준은 마지막 결정이 본 상태다. 직전 스텝과 비교하면 행동이 진행되는 동안 생긴 변화를 놓친다.

디사이더가 답해도 어댑터는 선택을 바로 적용하지 않는다. 프로필(profile)의 `decision_delay`만큼 게임 시간으로 기다린다(예: 0.2~0.35초). 그동안 실행기는 이전 행동과 반사를 계속 돌린다. 그 시점에 선택이 더 이상 합법이 아니면(대상 쓰러짐, 엄폐물 선점됨, 아이템 사라짐) 어댑터는 그 선택을 버리고 유지(hold)한다. 그리고 `dropped`를 기록하고 다음 결정 시점을 앞당긴다.

## 3.6 와이어 프로토콜 (JSON Lines, 버전 1)

게임에서 브리지로 가는 메시지는 stdout에 한 줄로 쓴다. 게임의 다른 출력과 구분하는 접두사를 붙인다.

```json
@@shakedown {"v":1,"type":"decide","run":"r042","step":5412,"t":90.2,"seq":37,
 "reason":"new_contact","profile":"cautious",
 "state":{"self":{"hp":{"thorax":72,"legs":40},"bleeding":["legs"],"stance":"crouch"},
          "equipment":{"mag":11,"spare_mags":2},
          "seen":[{"id":"e2","bearing":35,"range_m":18,"exposure":"upper_body","since_s":0}],
          "memory":[{"id":"e1","last_seen_s":6,"range_m":31}],
          "cues":[{"kind":"footsteps","bearing":-80}],
          "objective":{"goal":"extract_north","route_m":140,"time_left_s":372},
          "recent":[{"tactic":"withdraw","ended":"failed","seconds":5,"moved_m":0,"seconds_ago":1}]},
 "candidates":{"engage_e2":"Engage e2. 18 m, upper body exposed, 11 rounds",
               "cover_c1":"Move to cover c1. 6 m, 1.2 s exposed, blocks e2",
               "withdraw":"Withdraw south-west. 25 m",
               "hold":"Keep the current action"},
 "order_seed":991}
```

브리지에서 게임으로 가는 메시지는 stdin에 한 줄로 쓴다.

```json
{"v":1,"seq":37,"choice":"cover_c1","source":"jev",
 "probabilities":{"cover_c1":0.71,"engage_e2":0.18,"withdraw":0.09,"hold":0.02}}
```

그 밖의 메시지 유형:

| `type` | 방향 | 시점 | 내용 |
|---|---|---|---|
| `hello` | 게임 → 브리지 | 첫 결정 전에 한 번 | 프로토콜 버전, 게임 이름, 어댑터 버전, 시드, 프로필 |
| `decide` | 게임 → 브리지 | 결정 시점마다 | 위와 같음 |
| `end` | 게임 → 브리지 | 세션이 끝날 때 한 번 | 결과(`death`, `extract`, `timeout`, `oracle`), 스텝, 오라클 이름(있으면) |

규칙:

- 게임은 한 줄을 쓸 때마다 바로 stdout을 flush한다. 프로토타입에서는 파이프로 가는 stdout이 완전 버퍼링되어, flush를 추가하기 전까지 두 프로세스가 교착 상태에 빠졌다.
- `source`는 `random`, `mock`, `tape`, `jev`, `cache`, `fallback` 중 하나다.
- 요청 해시는 `state`, 정렬한 `candidates`, `order_seed`, `profile`, `step`을 포함한다. 실행 ID와 실제 시간 값은 뺀다. 이 값들을 넣으면 재실행할 때마다 불일치로 보이기 때문이다.
- 해시는 이 다섯 필드만 담은 객체를 정규 JSON으로 쓴 바이트의 SHA-256 16진수 값이다. 정규 JSON은 키를 정렬하고, 구분자를 공백 없는 `,`와 `:`로 쓰고, ASCII가 아닌 문자를 `\u` 이스케이프 대신 UTF-8로 쓰고, NaN과 Infinity를 거부한다. `tape:` 모드를 위해 게임 언어로 해시를 계산하는 어댑터는 이 바이트를 똑같이 만들어야 한다. 실수는 Python의 최단 왕복 표기와 같아야 하므로, 이 점에서도 `state`는 정수로 두는 편이 낫다.
- 브리지도 자기 쪽에서 같은 계약을 지킨다. 파싱이나 검증에 실패한 `decide` 줄, 두 번째 `hello`, 증가하지 않는 `seq`를 받으면 브리지는 게임을 멈추고 코드 2로 종료한다. 브리지가 `tape` 디사이더로 돌 때 요청이 테이프와 다르면 게임을 멈추고 코드 5로 종료한다.
- `seq`가 맞지 않거나, `choice`가 후보가 아니거나, 줄을 파싱할 수 없으면 게임은 코드 2로 종료한다. 계약 오류는 조용히 건너뛰지 않는다.

## 3.7 실행기와 반사

실행기는 전술 하나를 매 스텝 입력 이벤트로 바꾼다. 사람 플레이어와 같은 입력 경로를 쓰므로, 체력, 스태미나, 자세, 조준 산포는 사람을 제한하는 그대로 봇을 제한한다. 이벤트는 그 스텝의 입력 폴링 전에, 게임 자체 리플레이 시스템이 만드는 것과 같은 형태로 들어간다. 그래서 기록된 시각이 한 스텝씩 밀리지 않는다.

사람 같은 제한은 프로필에서 온다. 처음 본 뒤의 반응 지연, 커서가 대상에 자리 잡는 시간, 시드 기반 조준 흔들림이 여기에 속한다.

반사는 디사이더를 거치지 않는다. 대표적인 반사는 보이는 대상이 바뀔 때 다시 조준하기, 사격을 받을 때 질주 멈추기, 프로필의 반응 시간이 지난 뒤 수류탄 폭발 반경에서 뛰어나가기다. 반사는 전술을 대체하지 않는다. 다음 결정 시점을 앞당길 수만 있다.

프로토타입의 밤샘 실행에서는 수류탄 반사가 생기기 전, 사망의 39.5 %(1,071건 중 423건)가 폭발 때문이었다. 봇은 반응할 방법이 없는 위험에 죽고 있었다.

## 3.8 산출물

| 파일 | 요구 사항 |
|---|---|
| `telemetry.jsonl` | 줄마다 `t`, `step`, `type`을 가진 JSON 객체 하나. 최소한 `run_begin`, `contact`, `hit`, `damage_taken`, `death`, `extract`, `decision`, `run_end`를 쓴다. `decision` 줄에는 결정론적 필드만 담는다(`seq`, 스텝, 사유, 선택, 적용 또는 폐기). 지연 시간과 출처는 테이프에 둔다. |
| `inputs.json` | 주입한 모든 이벤트와 정확한 스텝 시각. 시각은 게임이 계산한 float 값 그대로 쓴다. 반올림한 시각은 긴 실행의 후반에 한 스텝 어긋날 수 있다. |
| `run_end` | 결과, 스텝, 걸은 거리, 최종 위치, 그리고 게임이 관심을 두는 카운트 |

`inputs.json`이 가장 쓸모 있는 산출물이다. 버그를 찾은 실행은 이 파일로 브리지와 모델 없이 재생된다. 여기에 assertion 몇 개를 더하면 게임 자체 테스트 스위트의 회귀 테스트가 된다.

## 3.9 종료 코드

| 코드 | 뜻 |
|---|---|
| 0 | 정상 종료. 결과는 텔레메트리에 있다. |
| 2 | 인자, 튜닝(tuning), 프로토콜 계약 오류 |
| 4 | 오라클이 중단함 |
| 5 | 테이프 불일치 |

코드 3은 게임이 이미 쓰고 있을 수 있어서 게임 몫으로 남겨 둔다(프로토타입은 리플레이 assertion 실패에 3을 썼다). 이 코드들을 이미 다른 용도로 쓰는 게임은 `shakedown.toml`에서 다시 매핑할 수 있다.

## 3.10 적합성 검사

`shakedown check-adapter`는 새 어댑터에 다음 검사를 돌린다. C1~C3은 프로토타입에서 통과했다(1.5절). C4~C6은 프로토타입의 단계별 인수 기준이었고, C7은 그곳에 작성할 테스트로 올라 있었다.

| 검사 | 통과 조건 |
|---|---|
| C1 반복 가능성 | 같은 인자로 돌린 `rule` 실행 두 번의 텔레메트리와 `inputs.json`이 바이트 단위로 같다 |
| C2 입력 재생 | 디사이더 없이 `inputs.json`을 재생하면 같은 게임 이벤트가 나온다(decision 줄 제외) |
| C3 테이프 재생 | `mock` 브리지 실행을 `tape:`로 재생하면 같은 텔레메트리(`run_begin` 제외)와 같은 결정 횟수가 나온다 |
| C4 계약 오류 | 잘못된 `seq`, 알 수 없는 선택, 깨진 줄이 각각 코드 2로 종료한다 |
| C5 불일치 | 변조한 테이프는 코드 5로 종료한다 |
| C6 오라클 | 강제로 만든 끼임 상태는 코드 4로 종료하고, 그 상태를 재현하는 `inputs.json`을 남긴다 |
| C7 누출 없음 | 벽 뒤의 개체는 `seen`에 한 번도 나타나지 않는다(게임별 픽스처. 에이전트 스킬이 템플릿을 작성한다) |

C1~C3이 모두 통과하는 것이 "이 게임은 지원된다"의 정의다. C1이 실패하는 흔한 원인은 실제 시간 기준으로 끝나는 작업이다. 비동기 에셋 로드, 밀리초로 잰 예산, 백그라운드 스레드가 그렇다. 호스팅된 디사이더를 기다리는 동안 이런 작업은, 빠른 테이프 실행에서는 받지 못할 실제 시간을 더 받는다. 해결책은 다음 스텝을 돌리기 전에 그런 작업을 시뮬레이션 스텝 기준으로 끝내는 동기화 지점이다.
