# 7. 밸런스 루프

M5 밸런스 루프는 사람이 내리는 디자인 결정에 쓸 증거를 만든다. `campaign --optimize`는 사람이 승인한 목표 범위에 맞춰 튜닝(tuning) 값을 탐색하며, 탐색에 쓰지 않은 시드(seed)에서도 결과가 유지될 때만 변경을 제안한다. `--optimize`가 없으면 M4의 기준선 한 라운드를 실행한다. 어느 모드도 기본값을 적용하지 않는다.

## 7.1 튜닝 키 표

게임은 튜닝 가능한 값을 키 표(key table)로 노출한다. Shakedown은 설정 파일을 기준으로 `tuning.keys` 경로를 읽는다. M5는 완전한 기준선을 고정할 수 있도록 모든 키에 문서화된 `default` 또는 `baseline`을 요구한다(아래 키와 범위는 예시다).

```json
{
  "keys": {
    "squad.fireTokens":        {"type": "int",   "min": 1,   "max": 4,   "default": 3,   "unit": "count"},
    "squad.tokenReturnSeconds":{"type": "float", "min": 0.2, "max": 1.5, "default": 0.7, "unit": "s"},
    "detection.baseRange":     {"type": "float", "min": 20,  "max": 70,  "default": 40,  "unit": "m"}
  }
}
```

실행(run) 하나의 튜닝 파일에는 값만 들어 있다.

```json
{"tuning_version": 1, "values": {"squad.fireTokens": 2, "detection.baseRange": 30}}
```

어댑터(adapter)는 모르는 키와 범위를 벗어난 값을 종료 코드 2로 거부한다. 튜닝 파일이 없으면 모든 기본값이 그대로 남아야 한다. 적합성 검사 묶음(conformance suite)은 게임의 키 표와 `tuning_keys.json`이 일치하는지 확인한다.

tinyraid는 이 표를 실제 범위와 기본값의 원본으로 읽는다. 다른 게임에서는 표가 기본값을 문서화하기만 할 수 있으므로, 사람이 제안 패치를 적용하기 전에 실제 게임의 읽기 경로를 확인한다. 제안은 표의 수치 기본값 필드를 바꾸며 임의의 게임 소스를 고치지 않는다. 표는 설정된 프로젝트 루트 안에 있어야 한다.

키는 게임이 중요한 지점에서 실제로 읽는 것으로 고른다. 프로토타입에서는 무기별 파라미터가 원뿔 키 두 개를 덮어썼다. 그래서 두 키를 모든 적 연사에 적용하는 배율 하나로 바꿨다. 이 배율은 상한보다 먼저 적용되므로, 1보다 큰 값은 장거리에서 잘린다. 이런 제약은 키 표에 기록해 둔다.

## 7.2 루프

1. 플래너(planner)가 `targets.json` 초안을 쓴다. 사람이 편집하고 승인한다.
2. 플래너가 `campaign.json`을 쓴다. 사람이 승인한다.
3. 오케스트레이터는 문서화된 기준선을 측정한 뒤 표준 라이브러리의 무작위·지연 격자 탐색으로 후보를 만든다. 모든 실험은 캠페인의 공통 `search_ranges`를 써야 한다. 실험마다 처음 `batch_size`개의 탐색 시드를 쓰며, 겹치는 프로필·맵 범위는 시드를 중복시키지 않고 합친다. 모든 범위에는 최소 `min_runs`개의 고유 시드가 필요하다.
4. 라운드마다 지표와 이상 신호를 집계한다. 기본 동작은 승인된 캠페인의 `rounds`에 따른 고정 일정이다. `planner_revisions = true`이면 설정된 플래너가 중단하거나 수치 범위를 수정한다. 수정은 승인된 탐색 범위로 잘라 기록하며, 키 추가나 정책 지시문 변경을 허용하지 않는다. 사람·모델 레이블은 자동 제공하지 않는다.
5. 탐색 지표로 후보를 정렬한다. `selection.json`은 보류 시드 실행 전에 측정된 개선 후보 중 상위 `top_k`개를 고정한다. 그 뒤에만 기준선과 선택한 후보를 예약된 보류 시드에서 한 번 실행한다. 탐색에 측정된 개선이 없으면 보류 시드를 쓰지 않는다.
6. 결정론적 게이트(7.4절)가 패치 출력을 통제한다. `report.md`는 캠페인 증거를 기록하며 `planner-report/`에는 보조 플래너 초안이 있다. 적용 여부는 사람이 정한다.

목표와 캠페인을 승인하기 전에 `[balance]`를 설정한다. 아래 예시는 번들 설정의 탐색 시드 밖에 있는 값을 사용하며, 실제 실험에서는 새 보류 시드를 정한다.

```toml
[balance]
method = "grid"
seed = 0
candidates_per_round = 4
grid_points = 3
holdout_seeds = [10007, 10009, 10037, 10039, 10061]
min_runs = 5
min_gain = 0.2
top_k = 1
max_runs = 1000
policies = ["rule", "mock"]
planner_revisions = false
policy_files = ["examples/tinyraid/__main__.py", "examples/tinyraid/game.py", "examples/tinyraid/adapter.py", "examples/tinyraid/probes.py"]
```

`method`는 `random` 또는 `grid`다. 위 값은 `method`, 필수 보류 시드와 `policy_files`, 명시적 정책을 제외하면 기본값이다. `policy_files`는 프로젝트 루트 기준으로 게임 실행기와 정책 소스를 나열한다. M5는 루트 안의 파일을 담은 비어 있지 않은 목록을 요구하며 브리지·디사이더·런타임 소스와 함께 해시를 고정한다. 정책은 생략하면 `batch.deciders`를 쓰며 오프라인 `rule`, `mock`, `random`만 허용한다. 보류 시드는 최소 `min_runs`개의 고유 정수여야 하며, 작은 배치가 쓰지 않는 탐색 시드까지 포함한 **모든** 설정 배치 시드와 분리돼야 한다. 실행 허용 검사는 출력 생성이나 자식 실행 전에 기준선·탐색·보류 검증의 최대 실행 횟수를 상한과 대조한다. `--max-runs`는 `balance.max_runs`를 낮출 수만 있다. 관련 설정을 바꾸면 새 승인 영수증이 필요하다.

M4 흐름과 같은 검토된 문서·영수증 경로에 모드 옵션을 추가한다.

```text
shakedown campaign --config CONFIG --campaign CAMPAIGN_JSON --approval CAMPAIGN_RECEIPT --targets TARGETS_JSON --targets-approval TARGETS_RECEIPT --output OUTPUT_DIR --approved --optimize
```

대문자 값은 운영자가 제공할 경로이며 실제 파일명이 아니다. 출력은 새 디렉터리를 쓴다. `balance_run.json`에는 실행 예산, 해시, 단계, 수정, 선택, 게이트, 제안 경로가 남는다. 탐색 지표와 보류 지표는 분리된다. 완료된 캠페인도 게이트가 거부되거나 미측정이면 제안이 없을 수 있다. CLI 성공을 밸런스 판정으로 읽지 않고 게이트를 확인한다.

## 7.3 봇 고정

튜닝 값을 비교하는 동안에는 봇 정책을 고정한다. 고정 대상은 디사이더(decider) 종류, 모델 ID, 프로필 지시문, 실행기(executor) 프로필이다. 튜닝과 봇이 함께 바뀌면 어느 쪽이 지표를 움직였는지 아무도 알 수 없다. 프로필 지시문을 바꾸면 새 캠페인(campaign)을 시작한다.

M5는 정책 지문을 기록하고 단계 사이에 승인 문서, 설정, 기본값, 지시문 파일, `policy_files`, 선언한 픽스처와 브리지·프로토콜·디사이더 소스가 바뀌지 않았는지 확인한다. 기준선과 후보는 같은 이름의 오프라인 정책, 실행 시간, 승인 프로필 지시문으로 실행한다. 지문은 선언하지 않은 외부 게임 코드의 동작까지 입증하지 않으므로 관련 게임 정책 소스를 모두 나열하고 런타임을 고정한다.

프로토타입은 이 규칙을 자기 변경에도 적용했다. `recent` 결과, 수류탄 반사(reflex), 루팅을 추가한 뒤에는 새 실행을 밤샘 실행과 비교하지 않았다.

게임을 맞춰 튜닝한 대상 봇은 사람의 플레이에서 멀어진다. 방어책은 세 가지다.

- 프로필을 하나만 두지 않고 여러 개 둔다(예: cautious, aggressive, looter).
- 사람 세션에도 같은 텔레메트리를 남겨 분포를 비교한다(실험 E5).
- **정책 민감도.** 제안하려면 서로 다른 검증 정책이 최소 두 개 필요하다. 한 정책의 목표 거리 점수는 개선되지만 다른 정책은 악화되면 정책 민감 후보로 거부한다. 예를 들어 `rule`·`mock`의 일치는 두 정책에서 관측된 선호만 입증한다. 사람 플레이와 호스팅 모델의 일치는 미측정이며, 정책 하나로는 민감도를 인증할 수 없다.

## 7.4 제안 게이트(proposal gate)

후보는 보류 시드에서 다음 조건을 모두 만족할 때만 변경 제안이 된다.

- 목표 범위를 벗어난 원래 단위의 거리를 확장된 목표·프로필·맵과 검증 정책에 걸쳐 합한 값이 기준선의 (1 − `min_gain`)배 이하이며 엄격하게 개선된다. 기본값은 `min_gain = 0.2`다. 기준선 거리가 0이면 변경을 제안하지 않는다.
- 모든 프로필·맵·정책 그룹의 오라클(oracle) 비율이 기준선보다 높지 않다. 오라클 측정은 그룹의 전체 분모를 포함해야 한다.
- 모든 기준선·후보 그룹에 최소 `min_runs`회의 유효 실행이 있고, 목표 지표마다 최소한 그만큼 측정된 관측이 있다. 누락·중복·검열·비유한 값·표본 부족은 `unmeasured`로 남으며 무효 실행은 제안을 차단한다.
- 최소 두 이름 있는 정책의 점수가 측정됐고 관측된 선호 역전이 없다.

통과한 후보는 `proposals/pNNN/defaults.patch`, `tuning.json`, `proposal.json`을 만든다. 영수증에는 원본 해시, 수치 기본값 변경, 점수와 목표별 값을 포함한 게이트 상세가 있다. 패치는 문서화된 키 표를 대상으로 하며 원본 파일은 그대로 둔다. 부트스트랩 구간은 기술적 증거이며 개선의 통계적 보장이 아니다. 자동 적용·빌드·테스트·롤백·기본값 커밋은 향후 설계이며 구현 명령이 아니다.

## 7.5 목표로 삼지 말아야 할 것

숫자 하나를 최대화하지 않는다. 생존율만 올리는 목표는 피해를 없애기만 해도 달성된다. 여러 지표의 범위를 프로필과 맵별로 동시에 쓴다: 생존율, 보상, 접촉당 사망, 첫 경고에서 첫 피격까지의 시간, 교전 길이, 탄약과 회복 사용량, 끼임과 시간 초과 비율.

목표 범위는 디자인 선택이다. 사람이 범위를 정하기 전에는 결과를 후보 사이의 비교로 읽고, 밸런스 판정으로 읽지 않는다.
