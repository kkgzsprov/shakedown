# 7. 밸런스 루프

밸런스 루프는 사람이 내리는 디자인 결정에 쓸 증거를 만든다. 루프는 사람이 승인한 목표 범위에 맞춰 튜닝(tuning) 값을 탐색한다. 변경 제안은 탐색에 쓰지 않은 시드(seed)에서도 결과가 유지될 때만 낸다.

## 7.1 튜닝 키 표

게임은 튜닝 가능한 값을 키 표(key table)로 노출한다. Shakedown은 그 사본을 `tuning_keys.json`으로 보관한다(아래 키와 범위는 예시다).

```json
{
  "keys": {
    "squad.fireTokens":        {"type": "int",   "min": 1,   "max": 4,   "unit": "count"},
    "squad.tokenReturnSeconds":{"type": "float", "min": 0.2, "max": 1.5, "unit": "s"},
    "detection.baseRange":     {"type": "float", "min": 20,  "max": 70,  "unit": "m"}
  }
}
```

실행(run) 하나의 튜닝 파일에는 값만 들어 있다.

```json
{"tuning_version": 1, "values": {"squad.fireTokens": 2, "detection.baseRange": 30}}
```

어댑터(adapter)는 모르는 키와 범위를 벗어난 값을 종료 코드 2로 거부한다. 튜닝 파일이 없으면 모든 기본값이 그대로 남아야 한다. 적합성 검사 묶음(conformance suite)은 게임의 키 표와 `tuning_keys.json`이 일치하는지 확인한다.

키는 게임이 중요한 지점에서 실제로 읽는 것으로 고른다. 프로토타입에서는 무기별 파라미터가 원뿔 키 두 개를 덮어썼다. 그래서 두 키를 모든 적 연사에 적용하는 배율 하나로 바꿨다. 이 배율은 상한보다 먼저 적용되므로, 1보다 큰 값은 장거리에서 잘린다. 이런 제약은 키 표에 기록해 둔다.

## 7.2 루프

1. 플래너(planner)가 `targets.json` 초안을 쓴다. 사람이 편집하고 승인한다.
2. 플래너가 `campaign.json`을 쓴다. 사람이 승인한다.
3. 오케스트레이터가 튜닝 후보(candidate)마다 N개 시드 × 프로필(profile) × 맵을 실행한다. 기본값은 N = 20이다. 시드는 탐색 시드와 보류 시드(holdout seed)로 나누며, 보류 시드는 마지막에만 쓴다.
4. 집계 → 레이블 → 플래너 `revise` → 옵티마이저가 키 표 안에서 다음 후보를 제안한다. 첫 옵티마이저는 표준 라이브러리로 만든 무작위 탐색과 격자 탐색이다.
5. 정해진 라운드 수가 끝나면 상위 후보를 보류 시드로 다시 실행하고, 플래너가 `report.md`를 쓴다.
6. 게이트(7.4절)를 통과한 후보가 있으면 Shakedown이 패치를 쓴다. 적용 여부는 사람이 정한다.

## 7.3 봇 고정

튜닝 값을 비교하는 동안에는 봇 정책을 고정한다. 고정 대상은 디사이더(decider) 종류, 모델 ID, 프로필 지시문, 실행기(executor) 프로필이다. 튜닝과 봇이 함께 바뀌면 어느 쪽이 지표를 움직였는지 아무도 알 수 없다. 프로필 지시문을 바꾸면 새 캠페인(campaign)을 시작한다.

프로토타입은 이 규칙을 자기 변경에도 적용했다. `recent` 결과, 수류탄 반사(reflex), 루팅을 추가한 뒤에는 새 실행을 밤샘 실행과 비교하지 않았다.

게임을 맞춰 튜닝한 대상 봇은 사람의 플레이에서 멀어진다. 방어책은 세 가지다.

- 프로필을 하나만 두지 않고 여러 개 둔다(예: cautious, aggressive, looter).
- 사람 세션에도 같은 텔레메트리를 남겨 분포를 비교한다(실험 E5).
- **정책 민감도.** 어느 튜닝 후보가 나은지를 두고 `rule` 디사이더와 모델 디사이더의 판단이 갈리면, 그 후보는 정책 민감(policy-sensitive)으로 표시한다. 정책 민감 후보는 사람의 플레이로 확인될 때까지 제안하지 않는다.

## 7.4 제안 게이트(proposal gate)

후보는 보류 시드에서 다음 조건을 모두 만족할 때만 변경 제안이 된다.

- 목표 범위를 벗어난 거리를 목표와 프로필에 걸쳐 합한 값이 기준선의 (1 − `min_gain`)배 이하다. 프로토타입의 기본값은 `min_gain` = 0.2였다.
- 오라클(oracle) 비율이 기준선보다 높지 않다.
- 모든 그룹이 최소 `min_runs`회 실행을 갖는다.
- 정책 민감이 아니다.

출력은 게임 기본값에 대한 패치와, 점수 및 목표별 값을 담은 보고서다. 프로젝트가 자동 적용을 선택했다면(5.4절), Shakedown은 편집 전후로 게임을 빌드하고 테스트를 실행한다. 새 실패가 하나라도 생기면 모든 파일을 되돌린다.

## 7.5 목표로 삼지 말아야 할 것

숫자 하나를 최대화하지 않는다. 생존율만 올리는 목표는 피해를 없애기만 해도 달성된다. 여러 지표의 범위를 프로필과 맵별로 동시에 쓴다: 생존율, 보상, 접촉당 사망, 첫 경고에서 첫 피격까지의 시간, 교전 길이, 탄약과 회복 사용량, 끼임과 시간 초과 비율.

목표 범위는 디자인 선택이다. 사람이 범위를 정하기 전에는 결과를 후보 사이의 비교로 읽고, 밸런스 판정으로 읽지 않는다.
