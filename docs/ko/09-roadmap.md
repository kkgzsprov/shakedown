# 9. 로드맵, 실험, 열린 질문

## 9.1 마일스톤

각 마일스톤은 네트워크와 키 없이 CI에서 통과하는 검사로 끝난다.

현재 구현은 M0~M7의 실행 경로다. M4는 구조화된 계획·승인·예산 기록, M5는 수치 탐색·고정된 보류 시드 게이트·검토용 패치, M6는 에이전트 스킬·두 번째 어댑터, M7은 Jev HTTP 결정을 제공한다. 구현·오프라인 픽스처·실제 공급자·범위를 한정한 블라인드 작성·사람 플레이 검증은 별도 주장이다. 실제 플래너·공급자 호출로 운영 동작을 입증하지 않았다. 로컬 검증과 현재 커밋의 CI도 별도 증거이므로 다른 플랫폼 통과를 말하기 전에 실제 실행을 확인한다.

| 마일스톤 | 내용 | 완료 조건 |
|---|---|---|
| M0 프로토콜 | `protocol.py`, `bridge.py`, `random`/`mock`/`tape` 디사이더(decider), 테스트용 가짜 게임 | 계약 오류 테스트와 불일치 테스트가 통과한다. CI의 여러 Python 버전에서 요청 해시가 안정적이다. |
| M1 tinyraid | 게임, 어댑터(adapter), `rule` 디사이더, 오라클(oracle), 텔레메트리, 입력 기록(input recording)과 재생 | tinyraid에서 C1~C6이 통과한다. 깨끗한 게임은 M1 시드(seed) 세트 전체에서 발견(finding)을 내지 않는다. |
| M2 배치(batch) 실행(run) | `shakedown.toml`, 오케스트레이터, 워커, 집계, `check-adapter` | tinyraid에서 60회 배치가 구간을 포함한 `metrics.json`을 만든다. `check-adapter`가 C1~C7을 보고한다. |
| M3 QA 경로 | 탐색, 이상 신호(anomaly), 분류(triage), 클립 | `shakedown bench tinyraid`가 보류 시드(holdout seed)에서 오라클 버그와 이상 신호 버그를 하나씩 따로 켰을 때 각각 잡아내고 재현한다 |
| M4 플래너 | 단계와 스키마, `claude-cli`, 명시적 restricted 설정의 `codex-cli`, `mock`, 예산 원장, 승인 영수증, 기준선 캠페인 한 라운드 | 오프라인 스키마·의미 제약·예산·승인·서브프로세스 픽스처·mock 캠페인 테스트가 통과한다. 두 실제 CLI는 별도 승인 예산으로 스키마를 수동 검증해야 한다. Codex의 도구 완전 제거는 인증하지 않는다. |
| M5 밸런스 | 키 표 기본값, 무작위·격자 옵티마이저, 제한된 캠페인 루프, 보류 시드 게이트와 검토용 패치 출력 구현 | tinyraid에 심은 목표를 사용하지 않은 보류 시드에서 검증하고, 게이트·루프 테스트로 증거 누락·정책 불일치·예산·낡은 승인을 검사한다. 구현 자체가 이 검증 증거는 아니다. |
| M6 스킬 | `skill/shakedown/`, 전송 골격·어댑터 가이드·래퍼와 Switchyard 얇은 실행기 예제 구현 | 배포 어댑터 적합성과 별도 새 컨텍스트의 독립 어댑터는 다른 증거다. 실험은 seed 7/depot/courier에서 C1~C3과 C4~C6을 통과했으며 C7은 미측정이다. 더 넓은 처음 보는 게임의 일반화는 미검증이다. |
| M7 호스팅 디사이더 | 고정 모델 `jev` HTTP 백엔드, 공유 캐시·예산·동시성, 제한된 재시도와 무효 실행 영수증 구현 | 로컬 HTTP 픽스처로 전송 경로를 검증하며 실제 추론·운영 지연·실제 청구액·모델 가치 비교는 미측정이다. |

M4는 mock 지표와 서브프로세스 픽스처로 유료 서비스 없이 검증할 수 있다. 실제 CLI 백엔드 검증에는 별도 수동 게이트와 명시적 호출 예산이 필요하다. M5는 이름을 기록한 오프라인 정책만 비교하며 호스팅 모델이나 사람 플레이와의 일치를 입증하지 않는다. M7의 토큰 추정과 예약 원장은 공급자의 실제 청구액을 입증하지 않는다. 어떤 구현 명령도 제안된 기본값을 자동 적용하거나 커밋하지 않는다.

## 9.2 1.0 출시 전 실험

이 실험들은 Shakedown의 봇이 결정의 근거로 삼을 만큼 좋은지 시험한다. 실험은 프로토타입 설계에서 나왔고, 이 문서를 쓴 시점에는 아직 실행하지 않았다.

| 실험 | 비교 | 보고 |
|---|---|---|
| E0 결정성 | `rule`로 같은 인자를 두 번 실행. 느린 모델 디사이더로 한 번 실행한 뒤 그 테이프(tape)로 실행 | 각 쌍의 텔레메트리가 바이트 단위로 같은지 |
| E1 디사이더 가치 | random 대 rule 대 모델 디사이더. 같은 후보(candidate)와 시드, 프로필(profile)별 | 생존율과 접촉당 사망에서 모델이 random을 이기는지. rule과의 비교 결과는 어느 쪽으로 나오든 보고한다. |
| E2 프로필 분리 | 프로필 지시문만 바꾼 모델 디사이더 | 전술 구성, 교전 거리, 세션 길이가 프로필마다 다른지. 다르지 않으면 플래너 → 디사이더 경로가 동작하지 않는 것이다. |
| E3 이름·순서 민감도 | 같은 결정 200개를 순서를 섞고 중립적인 이름(`cover_c1` → `opt_3`)으로 바꿔 다시 질문 | 최빈 선택의 일치도 |
| E4 지연 민감도 | `decision_delay` 0.1, 0.3, 0.6 s | 지표가 얼마나 움직이는지. 밸런스 실행은 값 하나로 고정한다. |
| E5 사람 비교 | 사람 세션의 텔레메트리 대 각 프로필 | 어느 프로필이 사람에 가장 가까운지. 이 프로필을 밸런스의 첫 기준으로 쓴다. |

E1에서 모델이 rule보다 낫지 않다고 나오면 밸런스 루프는 rule로 돌리고, 모델은 레이블링에만 쓴다. 그런 결과도 쓸모 있는 결과다.

## 9.3 이후

- 로컬 오픈 결정 모델(Laya, SemIf 등)을 디사이더로 써서 캠페인 전체를 오프라인으로 돌린다.
- 이 저장소에서 유지하는 엔진 어댑터. 기여자가 원하면 Godot을 먼저, 그다음 Unity와 Unreal을 둔다.
- 보정 세트와 시험 세트를 분리한 모델 기반 사망 레이블러. 임계값은 보정 세트에서 정하고, 정확도는 시험 세트에서 보고한다. 한 교전의 프레임은 두 세트에 함께 들어가지 않는다.
- Blender 대신 설정 가능한 인코더로 만드는 영상 클립.

## 9.4 열린 질문

| 질문 | 중요한 이유 |
|---|---|
| 라이선스 | 아직 정하지 않았다. 라이선스에 따라 스튜디오가 비공개 게임에 어댑터 템플릿을 넣을 수 있는지가 갈린다. 그런 용도에는 허용적 라이선스(MIT 또는 Apache-2.0)가 맞는다. |
| 프로토콜 버전 관리 | 브리지가 더 오래된 `v`의 어댑터를 어떻게 다루는가. 지금 브리지는 1이 아닌 `v`를 계약 오류로 거부한다. |
| 호스팅 디사이더의 속도 제한 | Jev 문서에는 나와 있지 않다. 이 값에 따라 M7의 워커 수가 정해진다. |
| 멀티플레이와 협동 게임 | 지금은 프로세스당 봇 하나다. 한 세션에 봇 여러 개를 두려면 결정 시점(decision point)마다 봇당 요청 하나가 필요하다. |
| 일시 정지할 수 없는 게임 | 권위 서버(authoritative server)를 쓰는 네트워크 게임은 시계를 멈출 수 없다. 이런 게임을 지원하려면 락스텝 재생을 포기해야 한다. |
