# 8. 예제 게임: tinyraid

`examples/tinyraid/`는 Shakedown과 함께 배포하는 작은 실시간 게임이다. 이 게임이 맡는 일은 세 가지다. 완전한 어댑터(adapter)를 보여 주고, 기여자에게 엔진 없이 돌려 볼 대상을 주고, 알려진 버그가 든 벤치마크로서 Shakedown의 변경을 측정할 수 있게 한다.

M1은 헤드리스 게임·어댑터·로컬 규칙·입력 기록과 재생·직접 결정 테이프 재생·선택적 PNG 프레임을 구현한다. M2는 배치와 적합성 검사를 추가하고, M3는 통제된 입력 워크플로 프로브·이상 신호 증거·검증된 분류와 재현·클립·아래 벤치마크를 추가한다.

## 8.1 게임

- 탑다운 2D, 연속 좌표, 고정 60 Hz 시뮬레이션 스텝, 시드(seed) 고정.
- 플레이어 한 명 대 경비병 몇 명. 벽, 엄폐물, 전리품 상자, 열쇠로 여는 잠긴 문 하나, 탈출 구역, 수류탄이 있다.
- 경비병은 시야 원뿔, 청각, 단순한 순찰-추격-수색 상태 기계를 갖는다.
- 세션은 사망, 탈출, 시간 제한 중 하나로 끝난다.
- Python 표준 라이브러리만 쓴다. 기본은 헤드리스다. 클립용으로 PNG 프레임 덤프(`zlib`로 작성)를 선택적으로 남긴다.

Python 게임은 실제 엔진이 가진 문제를 모두 보여 주지는 못한다. 다만 중요한 문제는 의도적으로 모델링할 수 있다(8.3절).

## 8.2 어댑터

어댑터는 `examples/tinyraid/adapter.py`에 있는 평범한 게임 코드다. 게임 규칙과 분리해 두었기 때문에 독자가 경계를 확인할 수 있다.

| 부분 | tinyraid 구현 |
|---|---|
| 관측 | 자기 자신, 장비, 벽을 고려한 플레이어 시야 원뿔 안의 경비병, 최근 본 경비병의 기억, 소음, 목표, 최근 전술 |
| 후보(candidate) | `engage_g<n>`, `cover_c<n>`, `withdraw`, `search_r<n>`, `heal`, `reload`, `loot_c<n>`, `use_door`, `extract`, `hold` |
| 실행기(executor) | 격자 A* 경로를 따른 이동, 반응 지연과 시드 고정 흔들림을 넣은 조준, 대상이 커서 아래에 오면 사격 |
| 반사(reflex) | 대상이 바뀌면 다시 조준, 반응 시간이 지나면 수류탄 반경에서 벗어남 |
| 규칙 디사이더(decider) | `rule` 모드의 짧은 임계값 규칙. 호스팅 백엔드 대체(fallback)는 계획 단계다 |
| 오라클(oracle) | 매 스텝 끼임, 순간이동, 수치, 플레이어·NPC 경계, 고체 충돌, "열쇠 없이 열린 문" 검사와 진행 없음 경고. M2는 크래시를 기록하고 M3 분류는 충실한 소스 증거가 있을 때 재현을 검사한다 |

어댑터는 다른 언어로 만든 게임과 똑같이 stdio로 3장의 프로토콜을 쓴다. 그래서 브리지는 이 게임을 C++나 Godot 게임과 구별할 수 없다.

## 8.3 심어 둔 버그

버그는 모두 기본으로 꺼져 있고 `--bug <name>`으로 켠다. 버그마다 잡아내야 할 메커니즘이 하나씩 정해져 있다. 그래서 벤치마크는 Shakedown의 어느 부분이 그 버그를 찾았는지 구별할 수 있다.

| 버그 | 무엇이 잘못되는가 | 잡아내야 할 메커니즘 |
|---|---|---|
| `corner_pocket` | 벽 모서리에 밀린 플레이어가 빠져나올 수 없는 구석에 갇힌다 | 끼임 오라클 |
| `thin_wall` | 충돌 틈이 있는 벽을 질주하는 플레이어가 통과한다 | 맵 경계 안에 있어도 잡는 고체 충돌 오라클(`solid_collision`) |
| `ammo_underflow` | 사격 중에 재장전하면 탄창이 −1이 된다 | 수치 오라클 |
| `door_no_key` | 잠긴 문이 반대편에서는 열쇠 없이 열린다 | 게임 고유 오라클 |
| `heal_overflow` | 체력이 가득 찬 상태에서 회복하면 체력이 최대치를 넘는다 | 수치 오라클 |
| `silent_grenade` | 한 경비병의 수류탄에 경고음이 없다 | 이상 신호(anomaly): 경고 없는 폭발 사망 |
| `extract_crouch` | 웅크린 상태에서는 탈출이 끝나지 않는다 | 이상 신호: 탈출 구역 안의 시간 초과 |
| `vision_leak` | 벽 뒤의 경비병이 `seen`에 나타난다 | 적합성 검사 C7 |
| `wallclock_load` | 백그라운드 "자산 로드"가 실제 시간(wall-clock) 기준으로 끝난다 | 느린 디사이더에서 적합성 검사 C1 또는 C3 실패 |

제어된 시나리오가 각 버그를 일으키는 입력 조건을 분리한다. 버그를 켜기만 해서는 규칙 봇이 그 위치나 조건을 반드시 방문하지 않는다. 테스트는 이 픽스처를 직접 실행한다. `wallclock_load` 주입은 의도적으로 호스트 시계를 읽는다. 호스트의 실행 시간에 따라 `asset_loaded` 텔레메트리 이벤트가 달라져, 결정 해시가 같더라도 C3의 텔레메트리 일치 검사가 실패한다. 결정성 실패를 보여 주는 픽스처이며, 지원되는 입력 재생 부하는 아니다.

## 8.4 벤치마크

루트 README의 편집 가능 설치 후 저장소 루트에서 전체 보류 시드 벤치마크를 실행한다.

```bash
python -m shakedown bench tinyraid --output runs/tinyraid-bench
```

`benchmark.json`과 `benchmark.md`는 자격에 필요한 커버리지와 합격 게이트를 구분한다. 주 검사는 `yard`, `cautious` 프로필, 오프라인 정책 세 가지(`rule`, `random`, `mock`), 입력 워크플로 일곱 가지를 쓴다. 정상 게임과 버그 하나만 켠 각 조건은 같은 고정 계획·정규화된 계획 해시·예산을 받는다. 탐지기는 오라클·텔레메트리 증거를 읽고, 채점기만 탐지·재현 후에 기대 버그 레이블을 적용한다.

고정 `m3-seeds.json`은 개발용 `[101, 211, 307]`과 보류 시드 `[1009, 2003, 3001, 4001, 5003, 6007]`을 분리한다. 기본 보류 검사는 워크플로 7개 × 정책 3개 × 시드 6개로 조건당 126회이며, 정상·버그 일곱 조건을 합쳐 재현·진단 전 1,008회다. 셀별 시드 풀을 모두 쓴 뒤 반복한다.

| 워크플로 | 검사하는 일반 입력·동작 |
|---|---|
| `navigate_corner` | 일반 어댑터로 모서리 픽스처를 탐색 |
| `sprint_wall` | 벽 쪽으로 질주한 뒤 이동 시도를 멈춤 |
| `reload_fire` | 일반 입력 경로에서 재장전과 사격을 함께 요청 |
| `heal_top_up` | 체력이 가득 찬 상태에서 회복 요청 |
| `unlock_door` | 열쇠 없이 잠긴 문의 반대편에서 열기 시도 |
| `grenade_escape` | 일반 보행을 억제하고 cautious 프로필의 위험 반사만 보존 |
| `crouched_extract` | 웅크린 채 탈출 시도 |

이는 명시된 통제 프로브이며 일반 플레이의 자율 발견을 뜻하지 않는다. 입력 생성은 심어 둔 버그 플래그로 분기하지 않는다. 정상·버그 실행은 같은 워크플로를 쓰고, 독립 입력 재생에서는 프로브 생성을 거치지 않는다.

주 재현율은 오라클 버그 다섯 개와 이상 신호 버그 두 개를 센다. 이상 신호 게이트는 측정 실행 최소 5회, 경고 없는 폭발 사망·탈출 구역 시간 초과 임계값 0.25, 측정된 정상 기준 배치를 고정한다. 의도적인 프로브 대기가 시간 초과 버그가 되지 않도록 이 시험대의 다른 범용 임계값은 1.0으로 고정한다. 일반 탐색은 본래 기본값을 유지한다. 보고서는 시그니처 기준 정밀도, 독립 재현된 재현율, 정상 발견, 실제 고정 예산 소비, 탐지 메커니즘을 포함한다. 첫 탐지 가능 실행 번호는 전체 예산을 마친 뒤 재구성한 값이며 실제 온라인 중단 시각이 아니다. 오프라인 서비스 비용은 0이다.

자격을 얻으려면 전체 보류 시드·정책·예산, 주 버그 일곱 가지, 적합성 진단 두 가지를 포함해야 한다. 합격에는 추가로 같은 계획, 정상 발견·무효 실행 0개, 모든 주 버그의 일치하는 메커니즘과 독립 재현이 필요하다. 개발용 또는 일부·디버그 커버리지는 선택한 버그가 재현돼도 미자격이다. `vision_leak`(C7)와 `wallclock_load`(자식 시계를 통제한 C3)는 별도 진단이며 주 재현율을 부풀리지 않는다. 시계 진단은 의도적으로 비결정적인 작업의 입력 재생 지원을 뜻하지 않는다.

결과는 이 픽스처 모음에서 Shakedown 메커니즘을 측정한다. 다른 게임의 미지 버그 발견을 추정하지 않으며, 보고용 시드로 튜닝한 결과는 독립 보류 증거가 아니다.

## 8.5 M1~M3 실행과 검증

저장소 루트에서 [루트 README의 명령](../../README.ko.md#돌려-보기)을 실행한다. `rule`, `bridge`, `tape:<file>`은 결정 경로를 선택한다. `--replay-inputs`는 세 경로를 모두 거치지 않고 기록된 전체 시작 설정을 읽는다. `cautious`, `aggressive`, `looter` 프로필은 반응·결정 지연과 조준 흔들림을 설정한다. 맵은 `yard`와 `warehouse`다.

`examples/tinyraid/m1-seeds.json`은 정상 인수 검사 조합을 고정한다. 시드 1, 7, 42 × 맵 2개 × 프로필 3개이며, 실행당 제한은 45초로 총 18회다. M1은 C1~C6 통과와 이 조합에서 오라클·계약 오류·테이프 불일치·크래시 발견 0개를 요구한다. 사망, 탈출, 정상 시간 초과는 유효한 게임 결과다. 이 유한한 개발용 조합은 M3 보류 시드 벤치마크의 재현율을 입증하지 않는다.

테스트에는 C7 벽 가림 픽스처, 자원 보존, 스텝별 이동·충돌, 심어 둔 수치·문·지형 버그, 지연된 결정 영수증도 있다. tinyraid의 끼임 검사는 최근 10초 중 스텝의 80% 이상에서 이동을 시도했고 누적 이동이 0.5 m 미만인지 본다. 짧은 경로 재계산 대기가 갇힌 플레이어를 숨기지 못하게 한다. 강제 끼임 시나리오는 코드 4의 오라클을 재현하는 입력 기록을 남긴다.

M2의 `examples/tinyraid/shakedown.toml`은 별도의 60회 배치(시드 0~9 × 맵 2개 × 프로필 3개, `rule`, 각 12초)를 추가한다. `--seconds 45`로 제한을 늘릴 수 있다. 루트 README에는 6회 스모크 실행 재정의와 범용 `check-adapter` 명령이 있다. 제공하는 오라클 픽스처는 `stuck`을 강제하고, 가시성 픽스처는 여러 스텝의 벽 뒤 경비병과 보이는 양성 대조군을 검사한다. 두 검사 모두 재생·프로세스 증거를 남긴다. 이는 적합성 검사이며 M3 탐색 재현율이 아니다.

그래픽 의존성이나 디스플레이 서버 없이 프레임을 덤프할 수 있다.

```bash
python -m examples.tinyraid --seed 7 --duration 12 --frame-dir runs/tinyraid-frames --frame-every 60
```

`--tuning`은 값만 담은 JSON 객체 또는 `tuning_version: 1`과 `values` 객체를 가진 형식을 받는다. 모르는 키나 아래 범위를 벗어난 값은 코드 2로 종료한다. 파일을 생략하면 기본값을 유지한다.

| 키 | 기본값 | 범위 |
|---|---|---|
| `player.speed` | 3.0 m/s | 1.0~5.0 |
| `guard.damage` | 8.0 | 1.0~20.0 |
| `guard.vision` | 10.0 m | 3.0~16.0 |

M3는 선택적인 `probe` 이름과 실제 시작 시나리오를 기록한다. 이전 일곱 필드 설정도 읽지만 게임 이벤트 해시는 엄격히 비교한다. 이전 텔레메트리·엔진 의미가 자동으로 바이트 호환되는 것은 아니며, assertion 불일치는 이관 성공이 아닌 실패다.
